**为什么这样选**

| 决策 | 选择 | 理由 |
|---|---|---|
| 前端构建 | Vite（不用 Next.js） | 纯后台 SaaS，不需要 SEO/SSR；Vite 简单、快 |
| UI 组件 | shadcn/ui（基于 Radix + Tailwind） | 组件代码直接放进项目、可改，风格接近成熟 SaaS，自带无障碍支持 |
| 服务端状态 | TanStack Query | 自动缓存、重新请求、加载/错误状态，避免手写大量 useEffect |
| 数据库迁移 | Flyway | 表结构有版本记录，可重复部署 |
| 认证 | JWT Access Token + Refresh Token | 前后端分离，扩展到 App/PWA 时可以复用 |
| 金额类型 | `DECIMAL(14,2)` / Java `BigDecimal` | 避免浮点误差，不用 double 存钱 |

## 2. 多商户（Multi-Tenant）设计 —— 最重要的部分

### 2.1 隔离方案：共享数据库 + `tenant_id` 字段

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 每个商户一个数据库 | 隔离最强 | 商户数一多，运维成本高 | ✗ |
| 每个商户一个 schema | 隔离较强 | 迁移复杂 | ✗ |
| **共享表 + tenant_id** | 成本最低，适合大量小商户 | 必须保证每条 SQL 都带 tenant_id | ✅ 采用，用下面四层防护弥补缺点 |

### 2.2 四层防护（层层兜底，防止串数据）

1. **身份层**：登录后选择商户，JWT 中写入 `tenantId` 和 `role`。后端**只信任 JWT 里的 tenantId**，前端传的 tenantId 一律忽略。
2. **ORM 层（自动）**：所有业务实体继承 `TenantEntity`，`tenantId` 字段使用 Hibernate 6 的 `@TenantId` 注解，配合 `CurrentTenantIdentifierResolver`：
   - 查询时 Hibernate **自动**追加 `where tenant_id = ?`；
   - 新增时**自动**写入当前 tenantId；
   - 开发人员不会因为"忘了写条件"而泄露数据。
3. **数据库层**：所有唯一约束都包含 tenant_id（例如 `UNIQUE(tenant_id, sku)`），所有外键查询加 `(tenant_id, …)` 复合索引。
4. **测试层**：每个模块都有"跨商户访问测试"：商户 A 的 token 访问商户 B 的资源 ID，必须返回 **404**（返回 404 而不是 403，不暴露资源是否存在）。

> 注意：原生 SQL（报表聚合）不经过 Hibernate 的自动过滤，**必须**手写 `tenant_id = :tenantId`，并由报表模块的隔离测试覆盖。

### 2.3 用户、商户、员工关系

- 一个 **用户（User）** 可以属于多个 **商户（Tenant）**，通过 `tenant_members` 关联，并带角色：
  - `OWNER` 店主：全部权限，可管理员工和订阅
  - `ADMIN` 管理员：除订阅/删除商户外的全部权限
  - `STAFF` 店员：录入销售、查看商品库存；不能看成本价和利润、不能删除数据
- 第一阶段：注册 → 创建商户 → 自己就是 OWNER。员工邀请放到第二阶段，但表结构从一开始就支持。
- 后端用 `@PreAuthorize("hasAnyRole('OWNER','ADMIN')")` 做接口级权限。

## 3. 关键业务规则（保证数据一致）

### 3.1 库存：流水账 + 当前库存

- `products.stock_qty` 保存当前库存（查询快）；`stock_movements` 保存每一次变动（可追溯）。
- **所有**库存变化只能通过 `InventoryService.applyMovement(...)` 一个入口完成，它在同一个数据库事务里：
  1. `SELECT … FOR UPDATE` 锁住相关商品行（多个商品按 id 排序加锁，避免死锁）；
  2. 校验库存（默认不允许负库存，商户可在设置中开启）；
  3. 更新 `stock_qty`，写入一条 `stock_movements`（记录变动前后数量、来源单据）。
- 不变量：`stock_qty == 所有 movements 的 qty_change 之和`。测试中会专门校验。

### 3.2 销售订单
- 创建即完成（MVP 不做草稿）：保存订单 → 扣减库存 → 记录每行**当时的成本价快照**（用于毛利计算）。
- 取消：状态改为 `CANCELLED`，按原数量写入反向库存流水，恢复库存。已取消订单不能再取消。
- 金额全部由**后端**计算（单价 × 数量 − 折扣），前端算的只用于显示，不被信任。

### 3.3 采购订单
- 状态流转：`DRAFT 草稿 → ORDERED 已下单 → RECEIVED 已收货`，任意未收货状态可 `CANCELLED`。
- 只有"确认收货"才增加库存，同时按**移动加权平均**更新商品成本价：
  `新成本 = (现库存×旧成本 + 收货数×采购单价) / (现库存 + 收货数)`。
- MVP 只支持整单一次收货；部分收货放到第二阶段（表里已预留 `received_qty`）。

### 3.4 价格
- 商品有 `retail_price`（零售价）和 `wholesale_price`（批发价）。
- 客户有 `price_tier`（RETAIL / WHOLESALE），开单选客户后自动带出对应价格，开单人仍可手动改单价。
- 第二阶段：`customer_prices` 表，为某个客户单独设置某商品的协议价。

### 3.5 单号
- 每个商户独立编号，例如 `SO-20261108-0001`、`PO-20261108-0001`，由 `tenant_sequences` 表加行锁生成，保证同一商户内不重复。

### 3.6 时间与时区
- 数据库统一存 UTC；商户有 `timezone`（默认 `Asia/Shanghai`）。"今日销售额""本月销售额"按商户时区计算日期边界。

## 4. 套餐、定价与开通方式

### 4.1 套餐

| 套餐 | 正价 | 限制与功能 |
|---|---|---|
| `FREE` 免费版 | 0 元，长期可用 | 商品 ≤ 100 个；1 个账号；商品、分类、库存、销售；仪表盘；报表只看近 30 天；无导出 |
| `STANDARD` 标准版 | 6.99 元/月 · 69.9 元/年 | 商品不限；+ 采购、客户、供应商、完整报表 |
| `PRO` 专业版 | 9.9 元/月 · 109.9 元/年（应收账款完成后开卖） | 标准版全部 + 批发价/客户协议价、应收账款、Excel 导出、最多 5 个员工账号 |
| **首月体验** | **1.99 元 / 首月** | 享受**标准版**全部功能 30 天；每个商户限用一次；到期后不自动扣费，未续费则回到免费版 |

- 所有限制集中定义在后端 `PlanPolicy` 一个类中（商品上限、账号上限、可用功能），以后调价或改权益只改这一处。
- 接口用 `@RequiresFeature(Feature.PURCHASING)` 之类的注解拦截；前端根据 `/auth/me` 返回的套餐显示"升级"提示，而不是直接隐藏菜单。
- 到期自动降级为免费版：**数据全部保留**，超出免费版的功能变为只读（能看历史，不能新增），不删除任何数据。
- 这里卖的是"**某期限内的使用权**"，不是买断，与需求书第 8 节一致。

> **双币种价格**：同时面向中国和马来西亚用户，价格按币种分别设置并存在数据库 `plan_prices` 表中（可在后台修改，无需改代码）。马币价格（2026-11-09 调价后）：首月体验 RM 1.00（仅标准版）· 标准版 RM 4.99/月 · RM 49.9/年 · 专业版 RM 6.9/月 · RM 69.9/年。（原定价 2026-11-08：标准版 ¥19.9/¥168、RM 12.90/RM 109；专业版 ¥39.9/¥328、RM 25.90/RM 209，已由 V9 迁移调整。）

### 4.2 开通方式一：激活码（小红书店铺销售）

```
用户在小红书店铺购买（首月体验 / 月付 / 年付）
        ↓  平台按虚拟商品规则发货
用户获得一个激活码，例如  SBZ-7KQ4-M2XP-9H3D
        ↓
登录 SmallBiz Manager → 设置 → 套餐与续费 → 输入激活码
        ↓
后端校验：码存在、未使用、未过期；首月码还要检查该商户是否从未用过首月体验
        ↓
开通/续期：到期时间 = max(现在, 当前到期时间) + 码对应的天数
```

- 激活码由平台管理员在 `/admin` 后台按批次生成（选择套餐、天数、是否首月体验码、数量），可导出为 CSV 上传到小红书发货。
- 激活码随机生成（去除易混淆字符 0/O/1/I），数据库只存哈希，兑换接口限速防止暴力猜码。
- 好处：交易完全在小红书平台内完成，不需要把用户引到站外付款，符合需求书第 9 节的合规要求；以后接入在线支付时，支付成功后内部调用同一个"兑换"逻辑即可。
- ⚠️ 上线前需确认小红书是否允许该类目以"激活码/卡密"形式销售软件服务，以及平台的发货方式。

### 4.3 开通方式二：站内扫码付款 + 人工审核

适用于直接访问网站的用户（不经过小红书店铺），支持两种收款方式：

| 收款方式 | 币种 | 适合用户 | 收款码图片 |
|---|---|---|---|
| 微信支付 | CNY 人民币 | 中国用户 | `assets/payment/wechat-pay.jpg` |
| Touch 'n Go eWallet（DuitNow 二维码） | MYR 马币 | 马来西亚用户（任意银行 App / 电子钱包均可扫） | `assets/payment/tng-duitnow.jpg` |

收款码作为**后台可配置项**（`payment_methods` 表，平台管理员上传图片、启用/停用），不写死在代码里；上面两张图片作为初始数据导入。

**流程**

```
① 商户 OWNER 进入「套餐与续费」→ 选择套餐与周期（首月体验 / 月付 / 年付）→ 选择付款方式
② 系统生成付款单：单号 + 应付金额 + 专属备注码（如 SBZ-7Q3K），显示对应收款码
   提示："付款时请在备注中填写 SBZ-7Q3K"；付款单 24 小时内有效
③ 用户扫码付款 → 回到页面点「我已付款」→ 上传付款截图，填写交易单号（选填）
   付款单状态：AWAITING_PAYMENT → PENDING_REVIEW（页面显示"审核中，通常 24 小时内完成"）
④ 你在 /admin/payments 看到待审核列表 → 对照微信 / TNG 收款记录（金额 + 备注码）核对
   ├─ 通过 → 系统自动开通/续期套餐（与激活码共用同一段开通逻辑），写入 plan_change_logs
   └─ 拒绝 → 填写原因（如"金额不符""未收到款项"），用户可重新提交
⑤ 商户在系统内收到结果通知（铃铛）
```

**规则**
- 应付金额由后端按 `plan_prices` 计算，前端只显示。
- 首月体验同样每个商户限一次（付款单创建时就检查，避免用户付了钱却开不了）。
- 付款截图属于私密文件：不能通过公开链接访问，只有该商户 OWNER 和平台管理员能查看。
- 同一个交易单号不能被两个付款单使用（防止一张截图重复提交）。
- 同一商户同时只能有一张未完成的付款单。

### 4.4 收款相关的风险提醒（上线前请确认）

1. **个人收款码用于经营**：你提供的微信码是**个人收款码**。按目前的监管要求，个人收款码用于持续的经营性收款可能被限制额度或功能；正式运营建议换成微信的**经营收款码**（个体户或小微商户可申请）。TNG 同理，长期经营可考虑 TNG / DuitNow 的商户收款。只是更换图片，系统不用改。
2. **小红书合规**：从小红书引来的用户，请**只通过小红书店铺（激活码）购买**；不要在小红书上引导用户到网站扫码付款。站内扫码只服务于直接访问网站的用户。
3. **人工审核的工作量**：每一笔都要你手动核对。用户量变大后应接入正式的在线支付（第二阶段），届时扫码通道可以关闭。
4. **退款**：需要在用户协议里写清楚退款规则；后台支持作废付款单并回退套餐。
5. **收入与税务**：跨境收款（人民币、马币）的申报与税务，按你所在地规定处理。

### 4.5 平台管理员

除商户内部的 OWNER/ADMIN/STAFF 外，增加一个**平台级**身份（`users.is_platform_admin`，只有你自己）：
- 查看所有商户列表（名称、套餐、到期时间、注册时间）——只看经营概况，不进入商户的业务数据；
- 手动为某商户开通/延长套餐（处理退款、补偿等特殊情况）；
- 生成和管理激活码批次；
- **审核扫码付款单；管理收款方式和各币种价格**；
- 管理客服话术库，查看未匹配的问题。

## 5. 安全基线

- 密码 BCrypt 加密；登录失败次数限制；密码最少 8 位。
- Access Token 有效期 2 小时；Refresh Token 30 天，以哈希形式存库，放在 `HttpOnly` Cookie，可吊销（退出登录即作废）。
- CORS 只允许自己的前端域名；所有输入用 Bean Validation 校验。
- 图片上传：限制类型（jpg/png/webp）和大小（≤ 2MB），重新生成文件名，存储路径带 tenantId。
- 统一错误格式：`{ "code": "PRODUCT_SKU_EXISTS", "message": "SKU 已存在", "details": {...} }`。

## 6. 智能客服（话术机器人 + 转人工）

### 6.1 定位
第一版**不调用大模型**，而是"关键词匹配 + 固定话术"的客服机器人：零成本、回答可控、不会胡编。以后如需更智能，可在同一个窗口里替换为大模型（只能基于话术库作答）。

### 6.2 交互流程

```
右下角 💬 按钮（登录页、注册页、系统内所有页面都有）
  ↓ 打开对话窗口
欢迎语 + 常见问题按钮：[怎么添加商品] [怎么开单] [套餐和价格] [激活码怎么用] [忘记密码]
  ↓ 用户点按钮或输入问题
后端匹配话术库（关键词 + 同义词打分）
  ├─ 匹配成功 → 显示标准回答（可带"去操作"跳转按钮，如 → 打开新增商品页面）
  │             并询问"这个回答有帮助吗？👍 / 👎"
  └─ 没匹配到，或连续 2 次 👎，或用户点"联系人工"
        → 显示人工客服卡片：
          "机器人暂时没能解决您的问题，请添加客服微信：Pianzibudehaosi_1A  [复制]
           添加时请备注：店铺名 + 问题简述"
```

### 6.3 设计要点
- **话术库存在数据库**（平台级，所有商户共用），在 `/admin` 后台增删改，不用改代码。首批内置约 30 条：注册登录、商品、库存、开单、取消订单、采购收货、报表、套餐价格、激活码、数据安全等。
- **微信号作为配置项**（`application.yml` 中的 `smallbiz.support.wechat-id`），不写死在代码里，以后更换只改配置。
- **记录未匹配的问题**（只记录问题文字和时间，不记录商户业务数据），在后台按出现次数排序，你据此补充话术。
- 客服接口不需要登录即可使用（登录页也要能问"忘记密码怎么办"），但做访问限速防刷。

### 6.4 合规提醒（重要）
- 客服微信**只显示在 SmallBiz Manager 自己的网站内**，作为产品的售后支持渠道。
- **不要**把微信号写在小红书笔记、评论、私信或商品详情中，也不要在小红书上引导用户"加微信购买"，否则可能被平台判定为站外引流而限流或处罚。
- 从小红书来的用户，付费只通过小红书店铺完成（见 4.2 激活码）；站内扫码付款（4.3）只服务于直接访问网站的用户。
- 客服话术中涉及付款的回答，只引导用户到「设置 → 套餐与续费」页面，不在聊天里发收款码。
